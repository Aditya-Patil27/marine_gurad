# A-H04 — Preserve event-time weather in report evidence

Status: COMPLETED after Codex continuation and verification. Owner A. B handoff H-04 and plan F06/F09. A-001/A-002A/B are complete; report routes are protected. Other reads remain public and B owns all frontend files.

## Objective

Remove the contradictory claim that no weather feed exists and allow a report creator to include actual event-time weather context in its hashed snapshot. Weather is contextual model output and must not change risk scores or imply an offence. Preserve existing reports and API compatibility.

## Scope and context

Read this brief, AGENTS.md, PROGRESS.md, relevant code in `apps/api/app/api/{weather,reports,vessels}.py`, `apps/api/app/services/risk_engine.py`, tests for weather/report/ocean context and `docs/contracts/USER_A_DATA_API.md`. Use targeted CodeGraph context where useful. The existing `weather.vessel_weather` fetches Open-Meteo wind/waves for the latest qualifying AIS gap, rejects time mismatch over one hour, and can return `available`, `unavailable`, or `not_checked`.

Allowed writes: `apps/api/app/services/risk_engine.py` (weather check text only), `apps/api/app/api/weather.py` and `reports.py` (weather context integration only), relevant tests under `apps/api/tests/`, `docs/contracts/USER_A_DATA_API.md` and `docs/contracts/AUTH_API.md`. No frontend, migrations/schema, provider keys, other routes, auth internals, dependency manifests, root docs or unrelated edits. Never call a live provider during tests or use the shared development database for destructive tests.

## Requirements

1. Replace the stale `No marine weather feed is connected yet` risk-check text with accurate wording: the behavioural engine has not checked weather; separately retrieved context is not proof or an automatic score change. Do not change scores, evidence states or thresholds.
2. Add an **optional**, explicit `include_weather_context` report request flag (default false for compatibility). When true, capture a fresh result from the existing event-time weather path, including source, model/observation distinction, event time, location, retrieval time and limitations whenever available. Preserve the original `available`, `unavailable` or `not_checked` status; no substituted current weather, fabricated values or silent fallback. If the existing endpoint lacks a metadata field, add accurate metadata without breaking its existing fields.
3. Add the weather context to `snapshot` **before** the canonical checksum is computed, with a statement it was fetched at report creation and may differ from what was displayed earlier. A provider failure should produce a truthful unavailable context, not make weather appear calm or silently omit it. Do not claim that previously displayed context was exactly the one reviewed.
4. Preserve the existing report authorization, CSRF, source-bound SST opt-in, legacy body, status codes and default report behavior. Ensure sync/async integration is safe for FastAPI's execution model; never call `asyncio.run()` inside an active event loop. Keep event-time lookup genuinely tied to gap data; no weather-only risk downgrade.
5. Add focused deterministic tests mocking the weather provider for available/unavailable/no-gap cases, verify capture happens before digest, old flag default compatibility and unchanged rule score; report actual results. Any DB integration must use explicit disposable `TEST_DATABASE_URL`; skipped checks are not passes. Update the existing contract with fields, retrieval time, limitations and frontend opt-in. B decides how to display the snapshot and owns `apps/web/**`.
