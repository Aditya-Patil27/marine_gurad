# SamudraSense shared agent contract

SamudraSense is a regional marine investigation prototype. Evidence supports human review; activity and ocean context do not prove illegal activity or predict global climate change. Code and actual verification determine implementation status.

Start with this file, `PROGRESS.md` and `tasks/current.md`; read other documentation, policy sections, skills and source only when relevant to the task. The complete preserved operating rules in `docs/AGENT_POLICY.md` remain binding; consult relevant sections by heading, not the whole file. `docs/FINAL_PRODUCT_PLAN.md` defines feature requirements and deadlines; `PLAN.md` maps tasks; `PROGRESS.md` is current status.

The implementation agent owns its assigned connected slice end to end: it implements, runs focused critical checks, updates task-owned documentation and marks the task **COMPLETED** when its stated acceptance criteria have evidence. Codex may audit later, but audit is not a gate before the next authorized task. Keep moving through eligible tasks without waiting for a separate review request. Do not independently redefine product scope. A owns `apps/api/**`, `infra/**` and API/data contracts; B owns `apps/web/**`, `docs/design/**`, `docs/demo/**` and frontend tests; C owns `ml/**` and evaluation only when assigned. One writer per file. Preserve all dirty, untracked and ignored user work.

Keep the existing React/Vite, FastAPI, PostGIS, Redis and Celery stack. Reuse existing components; minimize dependencies and avoid unrelated rewrites. Maintain compatible contracts, explicit UTC timestamps, WGS84 GeoJSON longitude/latitude, units, and accurate source/mode labels. Existing risk-engine internals use naive UTC; preserve boundary semantics. Load the Postgres skill before database/schema work, and the Supabase skill for Supabase work.

Use configured credentials locally without displaying them; never expose `.env`, keys, tokens or sensitive transcripts. Keep live, historical, cached and synthetic data separate. Record real provenance, permissions, uncertainty and acquisition status in `docs/DATA_MANIFEST.md`; do not invent results or download full xView3. Missing data is unknown. Bound retries and tool output; do not replace failures with invented success. No public API security claim until route protection is verified.

Use `docs/AGENT_HARNESS.md` for task lifecycle and CLI. Run only focused, necessary checks; use an isolated migrated test database, never reset/seed the shared database or delete volumes. The implementation report, changed code and focused evidence are sufficient to mark a bounded task complete; record skips and limits honestly. No unapproved pushes, deployment, purchases or external messages. Ask for genuinely missing access or consequential decisions; otherwise proceed within authorized scope.

For structural exploration use CodeGraph `codegraph_context` first, then one focused `codegraph_explore` if needed; use search/callers/callees/impact/files for the matching question. Do not repeat indexed exploration with grep or another agent. Use `rg` for literal text and direct reads of known files. Watcher updates lag about 500 ms. If CodeGraph reports uninitialized and `.codegraph/` is absent, ask whether to run `codegraph init -i`. Do not reinstall configured tools.

For low-TPM models, never resume an oversized session. Start a fresh session with a concise task-specific handoff, check estimated complete request size including system instructions and tool schemas before sending, and preserve full acceptance criteria in the task record. Limit individual tool outputs and split execution into reviewed slices; automatic compaction alone does not guarantee a per-minute request limit.

## Minimal implementation principles

Use the smallest complete change that meets the request. Before editing, understand the touched code and all affected callers, tests, fixtures, configuration and exports; use CodeGraph for structural questions and `rg` for literal text. Check for user-facing breakage, data loss or exposure, and contract changes. Reuse existing code and dependencies; do not add optional features, abstractions or configuration without a concrete need. Fix shared root causes, preserve validation and error handling, and prefer correct edge-case behavior when options cost the same. Add a focused check for non-trivial new logic; trivial edits do not need tests. Never cut trust-boundary validation, data-loss safeguards, security, accessibility or an explicit user requirement. State meaningful skips and remaining risks plainly.
